# Coterie Plan 3 — Pools & Cap Table Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** rewritten 2026-11-05 against `ios` `47d4475` and `backend` `510b5ce`. Not started.

**Goal:** a verified user can create a coterie, see it in Discover, open it, buy a share, leave before it fills, and see what they own, with the cap table always correct. No money moves in this plan.

**Architecture:** every write goes through `security definer` Postgres functions that take the caller from `auth.uid()`, so the rules hold against a direct API call. Clients get `select` only. The spec's `createPool` and `buyShare` Edge Functions aren't needed until Stripe is involved, and the payments plan wraps these database functions. iOS adds a `PoolRepository` and view models in the existing MVVM shape. Screens wait for mockups, so Phase 1 (Tasks 1–7) needs no designs and Phase 2 (Tasks 8–11) does.

**Tech Stack:** Postgres, pgTAP and Supabase Storage; Swift 6, SwiftUI, Swift Testing and supabase-swift 2.54.1.

**Spec:** `docs/specs/2026-08-07-coterie-mvp-design.md`, §2, §4, §5 and §6, as revised 2026-11-05.

## Decisions this plan rests on

Made by the user on 2026-11-05, and recorded in the spec.

| Decision | Result here |
|---|---|
| Card saved on joining, charged when full | Not built here. Buying a share is one server call with no payment step |
| No funding deadline, no term | No `funding_deadline` or `term_end_date` column |
| Round shares up to the penny | £2,000 across 3 is £666.67 |
| Photos | Creator uploads, with an optional product link |
| Per-use fee | Set by the platform. Stored as a placeholder of £25, not charged until the booking plan |

**This build must not reach real users.** Anyone can take a share for free until the payments plan lands.

## Global Constraints

- Migrations are forward-only. Every table needs an explicit `GRANT`. RLS scopes rows; grants scope columns.
- pgTAP runs as a superuser, so authorisation tests must use `set local role authenticated` with `request.jwt.claims`, or `has_table_privilege`.
- New `security definer` functions: `set search_path = public`, then `revoke all ... from public, anon` and `grant execute ... to authenticated`.
- "Coterie" in all user-facing copy; `pool` in the schema and code.
- Money is integer pence in the database and in `Money`. Never `Double`.
- DTOs use explicit `CodingKeys`, with a test against the snake_case JSON.
- Add no code comments unless a step asks for one. SwiftLint `--strict` must pass.
- Conventional commits, with no co-author trailers. Work on `feat/pools` in each repo.
- **Never run `make db-reset` or `supabase db reset` locally without asking:** it deletes the user's test accounts. Use `supabase migration up`.
- Do not trust a stub's shape: check response bodies against the real local stack (Task 4 Step 7).

## Review Focus

1. **Two people take the last slot together:** exactly one succeeds, and the other is told it has just filled. (Tasks 2, 6)
2. **A buy commits but the response is lost, and the user taps again:** "already an owner" reads as success. (Task 6)
3. **Publishing fails after photos have uploaded:** a retry does not upload them again. (Task 7)
4. **An uneven split:** the wizard's preview matches what the server stores, to the penny. (Tasks 2, 3)
5. **The last member leaves:** the coterie is cancelled and disappears from Discover. Leaving a full coterie is refused. (Task 2)

### Task 2: `create_pool`, `buy_share` and `leave_pool`

**Files:**
- Modify: `backend/supabase/migrations/0004_pools.sql` (not yet pushed, so still editable), `backend/supabase/tests/0004_pools_test.sql`, `backend/Makefile`, `.github/workflows/db-test.yml`
- Create: `backend/scripts/buy_share_race.sh`

**Interfaces:**
- Produces, all returning `public.pools`:
  - `create_pool(p_category pool_category, p_item_name text, p_brand text, p_description text, p_size text, p_condition text, p_source_url text, p_photos text[], p_target_amount integer, p_owner_count integer)`
  - `buy_share(p_pool_id uuid)`
  - `leave_pool(p_pool_id uuid)`
- Produces SQLSTATEs, which Task 4 maps:

| Code | Meaning |
|---|---|
| `CT001` | Caller isn't verified |
| `CT002` | Coterie is full or not open |
| `CT003` | Already an owner |
| `CT004` | Coterie not found |
| `CT005` | Not an owner |
| `CT006` | Invalid details |

Rules:
- **`create_pool`:** requires a verified caller. Trims `p_item_name` and `p_brand` and requires both. Requires size for shoes and stores null for bags. Requires 1–8 photos, each path starting with `<auth.uid()>/`. `p_condition` must be `new` or `pre_owned`, stored as `item_attributes -> 'condition'`. `p_source_url` is null or starts with `http://` or `https://`. Inserts the pool with `status = 'funding'` and `slots_filled = 1`, and the creator's membership, in one transaction.
- **`buy_share`:** verified check, then `select ... for update` on the pool, then the checks in this order: `CT004`, `CT003`, `CT002`. Inserts the membership and increments `slots_filled`. Sets `status = 'funded'` when `slots_filled = owner_count`.
- **`leave_pool`:** `select ... for update`, then `CT004`, `CT005`, and `CT002` if `status <> 'funding'`. Deletes the membership and decrements. Sets `status = 'cancelled'` at zero. A creator may leave; `creator_id` is kept as history.
