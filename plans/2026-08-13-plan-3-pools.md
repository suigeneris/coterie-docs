# Coterie Plan 3 — Pools & Cap Table — Implementation Plan

**Status:** draft, not started.
**Depends on:** Plan 1 (complete), Plan 2 (identity verification).

Plan 2 comes first because §4's "creating a pool requires `verification_status = verified`"
is only a real gate once something can actually set that column. Pools can be developed
against a test user marked verified by hand, so the dependency is soft — but shipping pools
before verification means shipping a gate that nothing enforces.
**Delivers:** a user can create a coterie, see it in Discover, open it, and join it — with the
cap table filling up correctly and the money boundary stubbed.

---

## Global Constraints

Everything in Plan 1's Global Constraints still applies. In particular:

- **Every migration that creates a table must `GRANT` explicitly**, and `update` grants must be
  column-scoped. RLS scopes rows; GRANTs scope columns. Both are required.
- **pgTAP runs as `postgres`, a superuser that bypasses RLS and grants.** Authorisation
  assertions must check the `authenticated` role explicitly via `has_table_privilege` /
  `has_column_privilege`, or `set local role authenticated` with `request.jwt.claims`.
- **Where a mock records call counts, assert them.** Result-only assertions let branch-routing
  bugs pass.
- **Commits: conventional-commit messages, no Claude co-author trailers.**
- DTO/DTI properties are camelCase with explicit `CodingKeys`, and each needs a round-trip test
  asserting the snake_case JSON keys.

New for this plan:

- **The §4 invariants are enforced in the database, never in the client.** The tab bar's `+`
  already gates creation on `verification_status`, but that is a UI convenience — it is not
  enforcement, and anyone with the anon key can bypass it. Every invariant below must hold
  against a direct PostgREST call with no app involved.
- **`slots_filled` is derived, never trusted from the client.** It is maintained by the same
  transaction that inserts a membership, or computed from `pool_memberships`. A client that can
  write it can oversell a pool.
- **Money is stubbed, not faked away.** `PaymentRepository` is a protocol from day one. The
  fake must be able to *fail* as well as succeed — a stub that always succeeds leaves every
  error path untested, which is how the sign-up error bug survived in Plan 1.
- **"Coterie" in all user-facing copy; `pools` in the schema.** Recorded in the design system
  doc under §10 Vocabulary.

## Task 1: `pools` & `pool_memberships` migration, RLS, verified-only enforcement

**Repo:** `backend`.

**Interfaces:** produces `public.pools` and `public.pool_memberships`, the `pool_status` and
`pool_category` enums, RLS policies, column-scoped grants, and a `pool_is_joinable` helper.

Columns per spec §4. `pools`: `id, creator_id, category, item_name, brand, description,
photos[], size, item_attributes jsonb, target_amount, owner_count, price_per_share,
per_use_fee, slots_filled, status, funding_deadline, term_end_date, created_at`.
`pool_memberships`: `id, pool_id, owner_id, joined_at`, `unique(pool_id, owner_id)`.

Constraints to encode in the schema itself, not in application code:

- `check (owner_count between 2 and 4)`
- `check (slots_filled >= 0 and slots_filled <= owner_count)`
- `check (category <> 'shoes' or size is not null)` — §2 makes size load-bearing for shoes
- `price_per_share` is **generated**: `target_amount / owner_count`. A stored column the client
  can set is a way to sell a £2,000 share for £1.

Grants:

```sql
grant select on public.pools to authenticated;
grant select on public.pool_memberships to authenticated;
-- No insert/update grant on either table. Both are written only through the
-- SECURITY DEFINER functions in Task 2, which is what makes the invariants unbypassable.
```

**Steps**

1. Write the migration with the enums, tables, checks and RLS.
2. RLS: `select` on `pools` allowed to any authenticated user for `status in ('funding',
   'funded', 'active')`, plus the creator's own drafts. Drafts must not be publicly listable.
3. RLS on `pool_memberships`: readable by any authenticated user — the cap table is public,
   it is what makes a pool trustworthy.
4. pgTAP: assert the checks reject `owner_count = 5`, a shoes pool with null size, and
   `slots_filled > owner_count`.
5. pgTAP: assert `authenticated` has **no** insert/update privilege on either table, using
   `has_table_privilege`. This is the test that proves the client cannot bypass Task 2.

**Verify:** `supabase test db` passes; `supabase db reset` applies cleanly.

## Task 2: `create_pool` and `join_pool` functions

**Repo:** `backend`.

Both are `security definer`, `set search_path = public`, and take the caller from `auth.uid()`
rather than a parameter — a `creator_id` argument is an impersonation hole.

`create_pool(...)` must:
1. Reject unless the caller's `profiles.verification_status = 'verified'` (§4 invariant 2).
2. Insert the pool with `status = 'draft'`, `slots_filled = 0`.
3. Return the new row.

`join_pool(pool_id)` must, in one transaction:
1. Reject unless the caller is `verified`.
2. `select ... for update` on the pool row — without this, two simultaneous joins both read
   `slots_filled = 3` and both insert, overselling a 4-person pool.
3. Reject if `slots_filled >= owner_count`, if `status <> 'funding'`, or if the caller is
   already a member.
4. Insert the membership and increment `slots_filled` in the same statement.
5. Flip `status` to `funded` when `slots_filled = owner_count`.

**Steps**

1. Write both functions. `revoke execute ... from public` then `grant execute ... to
   authenticated`, so anon cannot call them.
2. pgTAP: an unverified caller is rejected by both.
3. pgTAP: joining a full pool is rejected.
4. pgTAP: joining twice is rejected.
5. pgTAP: **concurrent joins do not oversell.** Two sessions, both at `slots_filled = 3` on a
   4-person pool; assert exactly one succeeds. This is the test the whole task exists for — a
   `for update` that is missing passes every sequential test.

**Verify:** `supabase test db` passes.

## Task 4: `PaymentRepository` protocol & fake

**Repo:** `ios`.

```swift
protocol PaymentRepository: Sendable {
    func payShare(poolID: UUID, amount: Money) async throws -> PaymentReference
}
```

`FakePaymentRepository` returns a synthetic reference. It must expose a configurable failure
mode and a call count, so the failure paths in Tasks 6–8 are actually exercised.

**Steps**

1. Protocol, `PaymentError` domain enum, `PaymentReference`.
2. Fake with `shouldFail` and `payShareCallCount`.
3. Register in `AppContainer`.
4. A comment on the protocol recording that Stripe replaces the implementation and nothing
   else — that is the point of the boundary.

## Task 5: `PoolRepository` protocol & Supabase implementation

**Repo:** `ios`.

```swift
protocol PoolRepository: Sendable {
    func discoverPools() async throws -> [Pool]
    func pool(id: UUID) async throws -> Pool
    func members(of poolID: UUID) async throws -> [PoolMembership]
    func createPool(_ draft: PoolDraft) async throws -> Pool
    func joinPool(id: UUID) async throws -> Pool
}
```

`createPool` and `joinPool` call the RPC functions from Task 2, not table inserts.

**Steps**

1. Protocol + `PoolRepositoryError` with a pure `mapped(_:)`, mirroring
   `SupabaseAuthRepository`. Map the Postgres error codes the functions raise onto domain
   cases: `notVerified`, `poolFull`, `alreadyJoined`, `offline`, `unknown`.
2. Implementation.
3. Tests for `mapped(_:)` — pure, no network, one per case.

## Task 7: Pool detail & joining

**Repo:** `ios`.

**Steps**

1. `PoolDetailViewModel`: loads the pool and its members; exposes whether the current user can
   join (verified, not already a member, pool not full, status `funding`).
2. `PoolDetailView`: item, funding status, cap table, and a buy-share action.
3. Joining calls `PaymentRepository.payShare` then `PoolRepository.joinPool`.
4. Tests, using the fake's failure mode: payment fails → no join attempted, error surfaced.
   Join fails after payment succeeds → **this is the case that needs a decision recorded**;
   see Risks.
5. Test that the join action is unavailable in every state that should forbid it.

**Repo:** `ios`.

Replaces `CreatePlaceholder`. Multi-step per §6; §14 requires step progress ("2 of 4").

## Risks & open decisions

1. **Payment succeeds, join fails.** The user has been charged and is not in the pool. This
   plan cannot resolve it properly without the real Stripe flow, but it must not be silently
   ignored. Task 7 should record the intended resolution — most likely: the payment is
   captured only after the join succeeds, which is what escrow means in §5. Decide before
   building Task 7.
2. **The fake payment repository is a lie by construction.** It cannot exercise 3-D Secure,
   partial captures, or webhook lag. Everything it validates is the app's own logic, not the
   integration. Do not let green tests here imply payments work.
3. **`price_per_share` as a generated column** assumes `target_amount` is exactly divisible by
   `owner_count`. £2,000 across 3 people is £666.67 with a penny left over. Decide where the
   remainder goes before writing the migration.
4. **Discover has no ranking, filtering or pagination** in this plan. Fine for a pilot with
   tens of pools; not fine later.
5. **Realtime is not included.** §6 calls the funding bar *"ticking up live via realtime"*.
   This plan gives a pull-to-refresh feed; realtime is a follow-up.
