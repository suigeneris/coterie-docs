# Coterie — CI Setup

**Goal:** every push to `coterie-ios` and `coterie-backend` is verified automatically, at
zero Actions cost.

**Status:** ✅ **Complete.** Both pipelines live and passing.

| Pipeline | Runner | Measured | Cost |
|---|---|---|---|
| `coterie-backend` — migrations + pgTAP | `ubuntu-latest` | **1m40s–2m08s** | ~2 billed min → ~1,000 runs/month free |
| `coterie-ios` — generate, test, lint | self-hosted `coterie-mac` | **23s** | zero |

---

## Decisions

| Decision | Choice | Why |
|---|---|---|
| iOS runner | **Self-hosted** on the dev Mac | GitHub-hosted macOS bills at a 10× multiplier — a 10-minute job costs 100 of the 2,000 included minutes, allowing ~20 runs/month. Self-hosted is free and faster, since Xcode, SPM and simulator caches stay warm. |
| Backend runner | GitHub-hosted `ubuntu-latest` | 1× multiplier. **Measured 2m08s** on the first run and **1m40s** after, so ~2–3 billed minutes — roughly 700–1,000 runs/month inside the 2,000-minute free allowance. Overage is ~$0.008/min. |
| QA/prod Supabase projects | **Deferred** | No pilot audience yet, and hosted projects cost money past the free tier. Migrations are forward-only and portable, so `supabase link` + `db push` will work unchanged whenever they are created. |
| Secrets | **Not yet needed** | Everything is local. The committed anon key is the standard local-dev JWT. Real keys only appear once QA/prod exist. |

## Backend pipeline — `coterie-backend/.github/workflows/db-test.yml`

Runs migrations from scratch and the pgTAP suite on every push and PR.

**Only Postgres is started.** The `auth` schema is created during database init rather than
by the GoTrue container, so all twelve other services are excluded — one image to pull
instead of twelve. Measured locally:

```
supabase start -x <everything but postgres>   17s   1 container
supabase test db                               1s   13/13 PASS
```

`supabase start` applies migrations itself on a fresh volume, so there is no separate
`db reset` step. The CLI version is pinned to `2.112.0` to match local development; bump it
deliberately rather than tracking `latest`.

## iOS pipeline — `coterie-ios/.github/workflows/ci.yml`

Runs `make generate`, `make test`, `make lint` on every push and PR.

Needs no backend: every test runs against mock repositories, and `AppEnvironment` reads
`Info.plist` rather than the network.

The runner daemon does not inherit an interactive shell's `PATH`, so the workflow prepends
`/opt/homebrew/bin` via `$GITHUB_PATH` — without it `xcodegen` and `swiftlint` are not found.

## The self-hosted runner — as installed

| | |
|---|---|
| Name | `coterie-mac` |
| Location | `~/actions-runner` |
| Version | `2.336.0` (osx-arm64, checksum verified against the release notes) |
| Labels | `self-hosted`, `macOS`, `ARM64` — the first two are what `runs-on` targets |
| Service | `~/Library/LaunchAgents/actions.runner.suigeneris-coterie-ios.coterie-mac.plist` |
| Persistence | `RunAtLoad: true` — starts on login, survives reboot |

**Gotcha worth remembering:** `./svc.sh start` *loaded* the LaunchAgent but never launched it
— `launchctl list` showed the label with PID `-`, and the runner stayed `offline`. Running it
from a shell outside the GUI session bootstraps into the wrong launchd domain. Fixed with:

```bash
launchctl kickstart -k "gui/$(id -u)/actions.runner.suigeneris-coterie-ios.coterie-mac"
```

Running `./svc.sh start` from Terminal.app directly would also have worked. This only affects
the *first* start; `RunAtLoad` handles it from the next login onward.

Useful commands:

```bash
cd ~/actions-runner
./svc.sh status                                        # is it running
./svc.sh stop && ./svc.sh start                        # restart
tail -f _diag/Runner_*.log                             # listener log
gh api repos/suigeneris/coterie-ios/actions/runners \
  --jq '.runners[] | "\(.name) \(.status)"'            # what GitHub thinks
```

The runner was registered and started programmatically; nothing is outstanding.

### Moving to a new machine

The runner is **tied to one Mac** — `~/actions-runner/.runner` holds credentials for that
specific registration, and nothing about it travels with a git clone. On a new laptop, after
the usual `make setup`:

```bash
cd ios && make runner        # scripts/setup-runner.sh
```

That script encodes the whole sequence performed by hand here: prerequisite checks, resolve
the latest runner release, download and **verify the checksum against the release notes**,
register with a freshly minted token (`--replace`, so re-running is safe), install the launch
agent, apply the `launchctl kickstart` workaround, and poll until GitHub reports `online`. It
finishes by listing any other registered runners so a decommissioned machine can be removed:

```bash
gh api -X DELETE repos/suigeneris/coterie-ios/actions/runners/<id>
```

The runner is named after the machine (`coterie-<ComputerName>`), so several Macs can be
registered at once and jobs go to whichever is online.

**Prerequisites on the new machine:** Xcode (see `.xcode-version`), Homebrew, `make bootstrap`
for `xcodegen`/`swiftlint`, an `iPhone 17 Pro` simulator, and `gh` authenticated as
`suigeneris`. The script checks all of these and fails with the fix rather than part-way
through.

**While no runner is online, iOS jobs queue rather than fail** — they run when one appears, so
a gap between laptops loses nothing.

## Notes

- **Self-hosted security:** the usual warning is that untrusted forks can run arbitrary code
  on your machine. `coterie-ios` is private with a single committer, so there are no
  untrusted forks. Revisit if the repo is ever opened up or gains outside contributors.
- **No untrusted input reaches any `run:` step** in either workflow, so the workflow-injection
  class of bug does not apply. Keep it that way — never interpolate `github.event.*` into a
  shell command.
- **Branch protection is unavailable, not merely unconfigured.** Both the classic
  branch-protection API and the newer repository-rulesets API return
  `403 Upgrade to GitHub Pro or make this repository public` for these private repos on the
  Free plan. So nothing enforces the checks server-side; they report status only.
  **Decision: skip.** With a single committer, CI reports breakage in ~25s and `main` can be
  fixed forward. **Revisit when** either a second person commits, or a production environment
  exists that a broken `main` could reach. Options at that point: GitHub Pro (~£4/month, which
  also raises the Actions allowance to 3,000 minutes), or a local `pre-push` hook running the
  suite — free, but client-side and bypassable with `--no-verify`.
- **No `KeepAlive` on the LaunchAgent.** If the runner process dies it will not be restarted
  until the next login. Acceptable for a single-dev setup; add `KeepAlive` to the plist if
  jobs start silently queueing.
- **`workflow_dispatch` is enabled on the iOS pipeline**, so runs can be triggered manually
  from the Actions tab or with `gh workflow run ci.yml`.
- **Concurrency cancels superseded runs.** Both workflows set `cancel-in-progress: true`, so
  pushing twice in quick succession shows the older run as `cancelled` — that is the setting
  working, not a failure.
- **Node 20 deprecation.** `actions/checkout` was bumped to `v5`. `supabase/setup-cli@v1` is
  still on the older runtime and is force-run on Node 24 by GitHub; it emits a warning, not a
  failure. Bump when upstream ships a newer major.
- **If the runner is offline, iOS jobs queue rather than fail.** They pick up when it comes
  back. Two runs were cancelled by hand during setup, before the runner existed.
